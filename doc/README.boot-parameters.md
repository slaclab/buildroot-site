# Boot parameters for NFS mounting and init scripts

This describes the parameters a target reads at boot to decide what to mount
over NFS and what script to run afterwards.

There are two independent ways to supply the NFS mount: the **kernel command
line** and **DHCP**. Both are supported and neither is deprecated.
They use different syntaxes, described separately below.

## Which source wins

The kernel command line takes precedence.

`S36fstab` runs early and, when it finds `ROOTMNT=`, writes the `/etc/fstab`
entry and marks it with a `#AUTOGENERATED_CMDLINE:` comment. `site.script`
(run later by udhcpc) checks for that marker and, if present, leaves
`/etc/fstab` alone -- **even if DHCP also supplied a root path for a different
mount point**. If you set `ROOTMNT=` on the command line, any DHCP-supplied
root path is ignored entirely.

With no `ROOTMNT=`, `S36fstab` prints `No ROOTMNT= in /proc/cmdline; falling
back to DHCP` and exits, leaving the DHCP path to do the work.

## Kernel command line

Set these in the bootloader configuration (pxelinux, iPXE, syslinux).

### `ROOTMNT=SRV:REMOTE_PATH:MNTPT`

Defines the mount. Three colon-separated fields: server, path exported by the
server, and local mount point. Required -- without it nothing happens and the
target falls back to DHCP.

    ROOTMNT=sdfhomenfs.sdf.slac.stanford.edu:/group:/sdf/group

The mount point directory is created automatically if it does not exist.

All three fields are required. A value with fewer than three fields is
rejected with `Malformed ROOTMNT=...` and the script exits without touching
`/etc/fstab`. Extra colon-separated fields beyond the third are ignored, so
`srv:/a:/b:/c` mounts `srv:/a` on `/b` and silently drops `/c`.

### `ROOTTYPE=nfs|nfs4` (optional, defaults to `nfs`)

Selects which **mount option profile** to use. It does *not* pin the protocol
version -- see "Version negotiation" below.

| Value                     | Profile used                     |
|---------------------------|----------------------------------|
| `nfs` (or absent)         | `$NFS_V3_OPTS` -- conservative, for servers expected to be v3-era |
| `nfs4`, `nfs4.1`, `nfs4.2`| `$NFS_V4_OPTS` -- for servers expected to speak v4 |

Anything starting with `nfs4` selects the v4 profile, so the older `nfs4.1`
form in existing boot configurations keeps working. The filesystem type
written to `/etc/fstab` is always normalised to `nfs`, because `mount.nfs`
never rewrites the type and `-t nfs4` cannot fall back to v3.

Note that **either profile can end up on any version** -- the profile only
chooses timeouts and caching behaviour, not the protocol version.

Caveat: a value that is neither `nfs` nor `nfs4*` (for example `ROOTTYPE=nfs3`)
is passed through to `/etc/fstab` verbatim with *empty* mount options, which is
almost certainly not what you want. Use `nfs` or `nfs4`.

### `ROOTOPTS=opt1,opt2,...` (optional)

Replaces the selected profile **entirely** -- it is not merged with it. Use it
only when you need something the profiles do not provide.

    ROOTOPTS=rw,hard,timeo=600,sec=sys

**Do not put `vers=` here.** It defeats version negotiation, which is the
whole point of the current setup. `vers=4` is especially misleading: it pins
**4.0**, the oldest v4 minor, rather than selecting "some version 4".

### `CMDLINE=path-or-url` (optional)

Sets the script or program to execute at the end of boot, handled by
`S90local`. Either a local path or a `tftp://host/path/file` URL, which is
fetched to `/boot/tftp/` and made executable first.

    CMDLINE=tftp://bootsrv.example.com/configs/site-init.sh

This value is `exec`'d, so it replaces the init script process. It takes
precedence over the legacy `/etc/bootfile` (written from the DHCP `boot_file`
option). `BOOTCMD`, if set in the environment, runs *before* either and does
not suppress them.

### Notes on parsing

Parameter names are matched at a word boundary, so a longer name that merely
ends with a known one (`MYROOTMNT=`, `XCMDLINE=`) is ignored. If a
parameter appears more than once, the **last** occurrence wins.

## DHCP

The DHCP root path (option 17, or an `IF_ROOTPATH` entry in
`/etc/network/interfaces`) is parsed by
`fs_skeleton/usr/share/udhcpc/site.script`. Two forms are accepted.

### `server:/path:/mountpoint`

The original form. Always uses the `nfs` option profile.

    sdfhomenfs.sdf.slac.stanford.edu:/group:/sdf/group

### `proto::server:/path:/mountpoint`

Adds an explicit protocol prefix. The **double colon is a required, fixed part
of the syntax** -- it is how the two forms are told apart, and it must not be
changed.

    nfs4::sdfhomenfs.sdf.slac.stanford.edu:/group:/sdf/group

`proto` selects the option profile on the same rule as `ROOTTYPE`: anything
starting with `nfs4` gets `$NFS_V4_OPTS`, anything else gets `$NFS_V3_OPTS`.
As on the command line, the prefix does not pin the protocol version.

This is the organisation's standard form for RTEMS boot configuration, which
is why it is also accepted here.

Known limitation: an **IPv6 server address** contains its own `::` and would be
misparsed as the protocol-prefixed form. Use a hostname for now.

## Mount option profiles

Both profiles are defined in one place, `/etc/default/nfsprofiles`
(`fs_skeleton/etc/default/nfsprofiles` in this repository):

    NFS_V4_OPTS="timeo=150,retrans=2,ro,nolock,noresvport,hard,noatime"
    NFS_V3_OPTS="ro,nolock,noresvport,noac,soft"

`S36fstab` and `site.script` both source this file, so editing it changes
both the command-line and DHCP paths together. Do not copy these strings back
into either script -- the two paths silently diverging is exactly what this
file exists to prevent.

## Version negotiation

Neither profile contains `vers=`, and that is deliberate. With no version
specified, `/sbin/mount.nfs` starts at **4.2** and walks down --
4.2 -> 4.1 -> 4.0 -> 3 -- until the server accepts. Targets therefore pick up
a server-side upgrade with no per-target reconfiguration.

Two details make this work, and both are easy to break:

- The negotiation ladder is a **userspace** feature of `mount.nfs`, not a
  kernel one. BusyBox's built-in `mount` handles `nfs*` types itself and calls
  `mount(2)` directly, which skips the ladder and lands on the kernel default
  (v3 for `nfs`, 4.0 for `nfs4`). `S42nfsmount` therefore invokes
  `/sbin/mount.nfs` explicitly for NFS entries in `/etc/fstab`, and leaves
  everything else to `mount -a`.
- The fstab type must be `nfs`, not `nfs4`, or the final v3 rung is
  unreachable.

To check what a running target actually negotiated:

    grep nfs /proc/mounts

The `vers=` shown there is the negotiated result. Seeing `vers=4.1` against a
server whose ceiling is 4.1 is the expected, correct outcome.

## Examples

A v4 server, mount read-only. Add this to the ipxe file, for the `set extra-args` argument:

    ROOTMNT=nfssrv.example.com:/export/root:/mnt/nfsroot ROOTTYPE=nfs4

Same, plus a CPU startup script:

    ROOTMNT=nfssrv.example.com:/export/root:/mnt/nfsroot ROOTTYPE=nfs4 CMDLINE=/afs/slac.stanford.edu/g/lcls/epics/iocCommon/cpu-b084-sp20/startup.cmd

A writable mount with a longer timeout, overriding the profile:

    ROOTMNT=nfssrv.example.com:/export/data:/mnt/data ROOTTYPE=nfs4 ROOTOPTS=rw,hard,timeo=600,retrans=2,noresvport

Equivalent via DHCP option 17, protocol-prefixed form:

    nfs4::nfssrv.example.com:/export/root:/mnt/nfsroot
